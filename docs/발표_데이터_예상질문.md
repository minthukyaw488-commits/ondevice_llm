# 발표 예상 질문 — 데이터(Data) 파트

> 1차 발표에서 **"어떤 데이터를 쓰고, 어떻게 처리했는가"** 부분에 대해
> 교수님·팀원이 물을 만한 질문과 답변을 정리했습니다. 답변은 실제 구현
> (`src/rag_pipeline.py`, 색인 결과 3,239 청크)에 근거합니다. 발표 때는
> **핵심 답변 1~2문장**만 말하고, 추가 질문이 오면 아래 근거를 덧붙이세요.

---

## A. 데이터 출처·구성

**Q1. 어떤 데이터를 사용했나요?**
- 핵심: 세 가지입니다 — ① 보건복지부 「2025 노인보건복지 사업안내(1·2권)」(정책 원문, PDF),
  ② 대전광역시 공개데이터(노인맞춤돌봄·재가노인 식사배달 현황 CSV, 실버시설 현황 XLS),
  ③ 대전시 공식 홈페이지의 독거노인 복지 안내(정제한 요약 문서).
- 근거: 모두 **공공기관이 공개한 자료**만 사용했습니다. 개인정보가 포함된 원천은 쓰지 않습니다.

**Q2. 데이터 규모는 얼마나 되나요?**
- 핵심: 문서를 정제·청킹해 **약 3,239개의 텍스트 청크**를 벡터 DB(ChromaDB)에 색인했습니다.
- 근거: 사업안내 PDF가 대부분의 분량을 차지하고, CSV/XLS의 각 행이 짧은 청크로 추가됩니다.

**Q3. 왜 대전 데이터를 골랐나요?**
- 핵심: 과제가 **대전 독거노인** 대상이라, 전국 공통 정책(사업안내)에 **대전 지역 특화 데이터
  (구별 시설·돌봄·식사배달 현황)**를 더해 "우리 동네에서 실제로 어디에 신청하나"까지 답하도록 했습니다.

---

## B. 데이터 형식·처리

**Q4. 어떤 파일 형식을 처리할 수 있나요?**
- 핵심: PDF, MD/TXT, **CSV, XLS/XLSX** 4계열을 자동 로딩합니다. 폴더에 넣으면 자동 색인됩니다.
- 근거: PDF는 pdfplumber(스캔본은 tesseract 한국어 OCR), CSV는 cp949/euc-kr 인코딩 대응,
  Excel은 pandas(openpyxl/xlrd)로 읽습니다. (`src/rag_pipeline.py`의 `load_documents`,
  `load_text_from_table`)

**Q5. 표(정형 데이터, CSV/Excel)는 어떻게 LLM이 이해하도록 넣었나요?**
- 핵심: 각 **행을 "컬럼명: 값, 컬럼명: 값 …" 형태의 한 문장**으로 바꿔 텍스트로 색인합니다.
  그래야 "○○구 재가노인 식사배달은 어디서?" 같은 질문에 표의 한 행이 검색됩니다.
- 근거: 표를 그대로 넣으면 임베딩이 의미를 못 잡기 때문에, 사람이 읽는 문장으로 평탄화(flatten)합니다.

**Q6. 데이터를 그냥 통째로 넣었나요, 전처리를 했나요?**
- 핵심: 전처리를 합니다 — ① **머리말/꼬리말·페이지번호·기호 잡음 제거**,
  ② **섹션 단위 청킹**(한국어 조문 표시 `제N조`, `1)`, `가.`, `①`, `○`, `#` 기준),
  ③ **저품질 청크(너무 짧거나 의미 없는 조각) 제거** 후 색인합니다.
- 근거: 정책 PDF는 반복 머리말·목차·쪽번호가 많아 그대로 색인하면 검색 정확도가 떨어집니다.

**Q7. HWP(한글 문서)는 왜 지원 안 하나요?**
- 핵심: 현재 미지원입니다. 공공기관 원문 상당수가 HWP라 **향후 과제**로 두었고,
  지금은 같은 내용을 PDF로 받아 처리합니다.
- 근거: HWP는 표준 파서가 불안정해 우선순위를 뒤로 뒀습니다. (README "향후 과제"에 명시)

## C. 개인정보·로컬 처리 (가장 중요, 자주 물음)

**Q8. 데이터를 클라우드에 올리나요? 개인정보는 안전한가요?**
- 핵심: **아니요. 전 과정이 기기 안에서 로컬 실행**됩니다. 색인·검색·재랭킹·LLM·음성인식 모두
  로컬이고, **어르신의 대화 내용은 절대 외부로 전송되지 않습니다.**
- 근거: 색인한 문서는 **공개 정책자료**이고, 실행 중 생성되는 개인적 대화(발화·이상신호)는
  기기/가정 네트워크를 벗어나지 않습니다. 클라우드 LLM API를 쓰지 않습니다.

**Q9. 그럼 색인된 문서에는 개인정보가 없나요?**
- 핵심: 없습니다. 색인 대상은 정책·시설 **안내 문서**뿐이고, 특정 개인의 정보는 넣지 않습니다.
- 근거: 대전 CSV/XLS도 "시설·서비스 현황"이지 수급자 명단이 아닙니다.

## D. 평가 데이터셋(eval set)

**Q10. 성능(정답률)은 어떤 데이터로 측정했나요?**
- 핵심: **자체 제작한 200문항 평가셋**(`data/eval/qa_200.jsonl`)입니다 —
  10개 복지 주제 × 15문항 = 150개 정보 질문 + 50개 범위 밖(거절 확인) 질문.
- 근거: 결과는 정답률 92%(정보 질문 95% / 범위 밖 안전 거절 84%), 재랭킹 적용 시 +14%p.

**Q11. 평가셋은 어떻게 만들었고, 한계는 없나요?**
- 핵심: 실제 어르신 말투(직설·구어·풀어쓰기)를 반영해 다양하게 작성했고,
  정답 기준은 **핵심 키워드 ANY-매치**입니다. 한계는 **자체 제작(held-out 미구성)·키워드 기반**이라,
  향후 **사람 평가/LLM 평가**로 보강할 계획입니다.
- 근거: 정직하게 한계를 밝히는 편이 신뢰를 줍니다. (README 평가 섹션에 한계 명시)

## E. 데이터 최신성·확장성

**Q12. 정책이 매년 바뀌는데 어떻게 최신으로 유지하나요?**
- 핵심: `data/welfare_docs/` 폴더에 **새 문서를 넣으면 자동 재색인**됩니다.
  매년 갱신되는 사업안내를 교체하는 방식으로 유지합니다.
- 근거: 코드 수정 없이 문서 교체만으로 갱신되도록 설계했습니다.

**Q13. 다른 지역(대전 외)으로 확장 가능한가요?**
- 핵심: 가능합니다. **전국 공통 정책 + 해당 지역 공개데이터**만 폴더에 넣으면 그 지역용이 됩니다.
- 근거: 파이프라인은 대전에 하드코딩돼 있지 않고, 데이터에 따라 동작합니다.

**Q14. GitHub에는 왜 샘플(sample) 문서만 있나요?**
- 핵심: 실데이터(보건복지부 PDF 등)는 **용량·배포 문제로 저장소에 커밋하지 않고**,
  재현용 **대체 샘플 문서**(`daejeon_welfare_sample.md`)만 포함했습니다.
- 근거: 실데이터는 로컬에서 폴더에 넣어 색인합니다. (문서 상단에 "샘플/대체 자료"라고 명시)

## F. 잘못된 답변 방지(데이터 신뢰)

**Q15. 데이터에 없는 걸 지어내지(환각) 않나요?**
- 핵심: **관련성 게이트**를 둡니다 — 검색 점수가 기준 미만이면 지어내지 않고
  "주민센터에 문의하세요"로 안전하게 안내합니다. 또 **비용·자격 같은 숫자는 근거에 있을 때만** 답합니다.
- 근거: 임베딩으로 후보 10개를 넓게 뽑고 cross-encoder로 재랭킹한 뒤, 상위 점수가 낮으면 거절합니다.
  (범위 밖 질문 안전 거절 84%)
